# RCTEST_VOFA 开发文档

> 面向接手本工程的嵌入式开发者。读完本文应能独立完成:编译烧录、改动控制逻辑、增删 VOFA+ 通道、判断哪些代码可以删。

## 1. 项目定位

一块 STM32H743 板子,通过串口与 **VOFA+** 上位机双向通信:

- **下行(上位机 → 板子)**:发送 ASCII 文本角度值(如 `45.5`),板子解析后驱动舵机。
- **上行(板子 → 上位机)**:以 **JustFloat** 二进制协议回传 `[占空比%, 当前角度°]`,VOFA+ 实时绘制曲线。

`上位机演示.mp4` 是这套链路的实机演示录像。

当前处于**原型验证阶段**:只有单路舵机(PD15)闭环,机械臂其余 5 路的驱动代码(`servo.c`)已随工程编译,但**未接入主流程**。详见第 8 节。

## 2. 硬件与时钟

### 2.1 芯片

| 项 | 值 |
|---|---|
| MCU | STM32H743VIT6(编译宏 `STM32H743xx`) |
| Flash | 2 MB,当前占用 **56 244 B(2.68%)** |
| RAM | DTCM 占用 3 264 B(2.49%),其余域为 0 |
| 外部晶振 | HSE 25 MHz(`HSE_VALUE`,见 `Core/Inc/stm32h7xx_hal_conf.h:109`) |
| 调试口 | SWD(PA13/PA14),经 ST-Link |

### 2.2 时钟树

```
HSE 25 MHz ──/PLLM=2──> 12.5 MHz ──×PLLN=64──> 800 MHz VCO ──/PLLP=2──> SYSCLK 400 MHz
                                                                          │
                                                        AHB /2 ──> HCLK 200 MHz
                                                        APB1/2/3/4 /2 ──> 100 MHz
                                                        APBx 定时器时钟 ──> 200 MHz
```

配置代码在 [Core/Src/main.c:257](Core/Src/main.c#L257) 的 `SystemClock_Config()`。

> **关键推论**:APB 分频系数不为 1 时,H7 的定时器内核时钟是 APB 时钟的 2 倍,即 200 MHz。这是第 2.4 节 PWM 频率计算的依据。

### 2.3 外设与引脚分配

| 外设 | 引脚 | 用途 | 状态 |
|---|---|---|---|
| TIM2_CH1 | PA0 | 机械臂关节 1 PWM | 编译在内,未接入 |
| TIM2_CH2 | PA1 | 机械臂关节 2 PWM | 编译在内,未接入 |
| TIM2_CH3 | PA2 | 机械臂关节 3 PWM | 编译在内,未接入 |
| TIM2_CH4 | PA3 | 机械臂关节 4 PWM | 编译在内,未接入 |
| TIM4_CH2 | PD13 | 机械臂关节 5 PWM | 编译在内,未接入 |
| TIM4_CH3 | PD14 | 机械爪 PWM | 编译在内,未接入 |
| **TIM4_CH4** | **PD15** | **舵机(当前主线)** | **使用中** |
| **USART2** | PD5(TX) / PD6(RX) | **VOFA+ 上位机链路** | **使用中** |
| UART5 | PB13(TX) / PB12(RX) | 小车通信(收,未解析) | 半接入 |
| USART3 | PB10(TX) / PB11(RX) | 预留 | 仅初始化 |
| UART7 | PE8(TX) / PE7(RX) | 预留 | 仅初始化 |
| GPIO | PC1 | 推挽输出,初始低 | 未使用 |
| GPIO | PD4 | 输入,无上下拉 | 未使用 |

引脚映射可在 [Core/Src/tim.c:185](Core/Src/tim.c#L185) 和 [Core/Src/usart.c:209](Core/Src/usart.c#L209) 的 `HAL_*_MspPostInit/Init` 中查到。

### 2.4 PWM 定时器参数

TIM2 / TIM4 使用**完全相同**的基础配置([Core/Src/tim.c:45](Core/Src/tim.c#L45)、[tim.c:111](Core/Src/tim.c#L111)):

| 参数 | 值 | 推导 |
|---|---|---|
| Prescaler | 199 | 200 MHz / (199+1) = **1 MHz** 计数频率 |
| Period (ARR) | 19 999 | 20 000 计数 / 1 MHz = **20 ms → 50 Hz** |
| 模式 | PWM1,高电平有效 | — |

**这是整个工程最重要的一个约定:计数频率恰好 1 MHz,所以「比较值 = 微秒数」。**
`servo_angle_to_pulse()` 直接返回 500~2500 这样的微秒值,不需要任何单位换算。

## 4. 构建系统架构

### 4.1 分层设计

构建系统是**两层 CMake**,这是理解本工程的关键:

```
CMakeLists.txt (顶层)                    ← 用户的地盘
  ├── add_subdirectory(cmake/stm32cubemx)   ← ST 生成的地盘
  ├── target_sources(...)  Core/Src/servo.c, Core/Src/math.c
  └── target_link_libraries(stm32cubemx)

cmake/stm32cubemx/CMakeLists.txt         ← 工具生成,不手改
  ├── set(MX_Application_Src  main.c gpio.c tim.c usart.c ...)
  ├── set(STM32_Drivers_Src   stm32h7xx_hal_*.c ...)
  ├── add_library(stm32cubemx INTERFACE)   ← 只传 include 路径和宏
  ├── add_library(STM32_Drivers OBJECT)    ← HAL 源码编成对象库
  └── target_sources(${CMAKE_PROJECT_NAME} PRIVATE ${MX_Application_Src})
```

**设计意图**:把「工具会重新生成的内容」全部隔离在 `cmake/stm32cubemx/` 下。顶层 `CMakeLists.txt` 顶部那句注释说的就是这个:

> *This file is generated only once, and is not re-generated if converter is called multiple times. User is free to modify the file as much as necessary.*

所以**新增自己的源文件,只改顶层 `CMakeLists.txt`**,重新生成时不会丢。

### 4.2 当前顶层挂载的用户文件

```cmake
target_sources(${CMAKE_PROJECT_NAME} PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/servo.c
    ${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/math.c
)

list(REMOVE_ITEM CMAKE_C_IMPLICIT_LINK_LIBRARIES ob)

# newlib-nano 默认裁掉浮点 printf,这里强制链回来
target_link_options(${CMAKE_PROJECT_NAME} PRIVATE -u _printf_float)
```

`-u _printf_float` 是为 `servo.c` 里带浮点的 `printf` 服务的;主流程 `main.c` 不依赖 printf。**若日后删掉 `servo.c`,这个链接选项也应一并删除,否则白白增大代码体积。**

### 4.3 工具链

由 `CMakePresets.json` 的 `toolchainFile` 指向 `cmake/gcc-arm-none-eabi.cmake`,使用:

- 编译器:`arm-none-eabi-gcc` 14.3.1(st.2)
- 生成器:Ninja 1.13.2
- 标准:C11,`CMAKE_C_EXTENSIONS ON`

两者都来自 **STM32CubeCLT / STM32 VS Code 扩展的 bundle 仓库**,默认位于 `%LOCALAPPDATA%\stm32cube\bundles`。`cube-cmake` 是 ST 包装过的 cmake 入口(见 [.vscode/settings.json](.vscode/settings.json))。

### 4.4 编译产物

输出到 `build/Debug/RCTEST_VOFA.elf`(及同名 `.map`)。`build/` 已在 [.gitignore](.gitignore) 中。

## 5. 运行时架构

### 5.1 核心思想:中断只做搬运,主循环做一切

这是 `main.c` 里最重要的架构决策。中断服务例程**不做任何浮点解析、不打印、不等待**——它只把收到的字节搬进缓冲区并置一个标志位,真正的工作全部留给主循环。

```
                      ┌──────────────────────────────────────┐
   VOFA+ 上位机        │           中断上下文 (USART2_IRQn)     │
   "45.5\n"  ────────> │  HAL_UART_IRQHandler                  │
                      │    └─ 检测到 IDLE 事件                 │
                      │        HAL_UARTEx_RxEventCallback()   │
                      │          ├─ memcpy → rx_line[]        │
                      │          ├─ rx_line_ready = 1         │
                      │          └─ 重新武装接收 ◄── 必须!     │
                      └───────────────┬──────────────────────┘
                                      │ 标志位
                      ┌───────────────▼──────────────────────┐
                      │          主循环 (20 ms 周期)           │
                      │  1. 快照 rx_line,清标志                │
                      │  2. strtof → target_angle,限幅         │
                      │  3. 斜坡逼近 → current_angle            │
                      │  4. CCR = servo_angle_to_pulse()      │
                      │  5. vofa_send(占空比, 角度)            │
                      │  6. busy-wait 对齐到 20 ms            │
                      └───────────────┬──────────────────────┘
                                      │ JustFloat 12 字节
   VOFA+ 示波器  <────────────────────┘
```

### 5.2 为什么不用「中断里直接解析」

`strtof` 是 newlib 的浮点解析,执行时间不确定,最坏情况可达数百微秒。放在 UART 中断里会:

1. 阻塞同优先级及更低优先级中断;
2. 与主循环的 PWM 更新竞争,产生抖动。

因此 `rx_line_ready` 标志位 + 主循环解析是**正确**的设计。

### 5.3 临界区

`rx_line` 是 32 字节数组,**不是原子对象**。主循环复制它时必须屏蔽中断,否则可能读到「半新半旧」的内容:

```c
__disable_irq();
memcpy(snapshot, rx_line, sizeof(snapshot));
rx_line_ready = 0;
__enable_irq();
```

注意 `__disable_irq()` 会屏蔽**所有**中断(含 SysTick)。这里拷贝 32 字节耗时约几十个时钟周期,在 400 MHz 下可忽略,是合理的权衡。

### 5.4 接收状态机:为什么必须重新武装

`HAL_UARTEx_ReceiveToIdle_IT()` 是**一次性**的:收到一帧(IDLE 事件)或缓冲填满后,HAL 会把接收状态复位、关闭 IDLE 中断。**不在回调里重新调用一次,链路就永久死掉。**

```c
HAL_UARTEx_ReceiveToIdle_IT(&huart2, PC_RXbuff, sizeof(PC_RXbuff));
```

`HAL_UART_ErrorCallback()` 里也做了同样的重新武装,用于从溢出/帧错误中恢复。

**触发时机的精确语义**(已核对 HAL 源码 `stm32h7xx_hal_uart.c`):

| 条件 | 是否回调 | 传入 Size |
|---|---|---|
| 收到 ≥1 字节后线路空闲(IDLE) | 是 | 已收字节数 |
| 缓冲区被填满(50 字节,无空闲) | 是 | 50(`RxXferSize`) |
| 收到 0 字节的 IDLE | **否** | — |

> 第二行是一个**健壮性隐患**:若上位机一次发来超过 50 字节且中间无空闲,整块会被当成"一行",再被截断到 31 字节交给 `strtof`。不会崩溃(回调内会重新武装,链路能恢复),但会解析出错误角度。规避办法是约定上位机每帧不超过 31 字节并以换行结尾,或改用 DMA + 环形缓冲。

### 5.5 时序保证

主循环用忙等对齐周期:

```c
const uint32_t tick = HAL_GetTick();
...
while ((HAL_GetTick() - tick) < CTRL_PERIOD_MS) { }
```

不用 `HAL_Delay()` 的原因:后者依赖 SysTick 中断,精度受中断延迟影响;忙等直接读计数器,抖动更小。

**代价**:主循环绝大部分时间在空转,CPU 利用率极低。对当前原型(只控一路舵机)完全可接受;若日后要加传感器采集、多轴联动,这个忙等必须换成基于定时器中断的状态机或 RTOS 任务。

## 6. VOFA+ 通信协议

### 6.1 上行:JustFloat 帧

VOFA+ 的 JustFloat 协议规定:**N 个 float 小端排列,后跟固定的 4 字节帧尾 `00 00 80 7F`**。

那 4 字节其实是**大端表示的 `+Inf`**:

```
0x7F800000  =  +Inf   (float 的正无穷,IEEE 754)
   ↓ 按小端写入内存
00 00 80 7F
```

VOFA+ 靠扫描这个不可能出现在正常数据中的模式来切分帧,所以**帧尾位置错一个字节,整条曲线全乱**。

本工程的数据结构([Core/Src/main.c:28](Core/Src/main.c#L28)):

```c
#define CH_COUNT 2                      /* 通道数：占空比(%) + 当前角度(°) */
typedef struct {
    float         fdata[CH_COUNT];
    unsigned char tail[4];
} VofaFrame;

_Static_assert(sizeof(VofaFrame) == sizeof(float) * CH_COUNT + 4U,
               "VofaFrame has unexpected padding");
```

**`_Static_assert` 是这个设计里最值得称道的一笔**:编译器可能在 `tail` 前插入填充字节使 `sizeof` 变大,那样帧尾就不在预期偏移上,上位机解析必然失败。这条断言把「运行期莫名其妙的曲线错乱」提前变成了「编译期报错」。

当前帧长 = 4×2 + 4 = **12 字节**。

| 偏移 | 内容 | 说明 |
|---|---|---|
| 0..3 | `float` 占空比 | 2.5% ~ 12.5% |
| 4..7 | `float` 当前角度 | -90.0 ~ +90.0 |
| 8..11 | `00 00 80 7F` | 帧尾 |

在 VOFA+ 里选 **JustFloat** 模式,波特率 **115200**,即可看到两条曲线。

### 6.2 下行:ASCII 文本

上位机以**纯文本**发送目标角度,如 `45.5`(可带换行)。板子侧走「空闲中断收一行 → `strtof` 解析」的路径。

选择 ASCII 而非二进制下行的原因:调试时可以直接用串口助手手敲数字,无需构造二进制帧。上行用二进制是为了带宽和精度。

### 6.3 带宽核算

| 方向 | 帧长 | 周期 | 速率 |
|---|---|---|---|
| 上行 | 12 B | 20 ms | **600 B/s** |
| 链路容量 | — | 115200 8N1 | 11 520 B/s |

占用约 **5%**,余量充足。上位机以 ~50 Hz 采样,曲线足够平滑。

### 6.4 舵机映射约定

```c
static uint32_t servo_angle_to_pulse(float angle)
{
    if (angle < SERVO_ANGLE_MIN) angle = SERVO_ANGLE_MIN;   // -90
    if (angle > SERVO_ANGLE_MAX) angle = SERVO_ANGLE_MAX;   // +90
    return (uint32_t)(((angle + 90.0f) / 90.0f + 0.5f) * 1000.0f);
}
```

| 角度 | 脉宽(比较值) | 占空比 |
|---|---|---|
| -90° | 500 → 0.5 ms | 2.5% |
| 0° | 1500 → 1.5 ms | 7.5% |
| +90° | 2500 → 2.5 ms | 12.5% |

因为计数频率是 1 MHz,返回值直接就是微秒数。**这套约定与 `servo.c` 的 `translate_angle_to_pulse()` 保持一致**,两边可以互换。

> 注意公式里的 `+ 0.5f` 是在**加 90 之后**加的,作用是让 0° 落在 1500 µs 而非 1000 µs——即把 `[-90,90]` 线性映射到 `[500,2500]` 的标准写法。它是「归一化公式」的一部分,不是四舍五入偏置。

### 6.5 斜坡限速

目标角度由上位机瞬间给定,但舵机不能瞬间转到位(会堵转、抖动、拉低电源)。主循环用**每周期 1°** 的固定步长逼近:

```c
if (current_angle < target_angle) {
    current_angle += SERVO_SLEW_STEP;        // 1.0f
    if (current_angle > target_angle) current_angle = target_angle;   // 防过冲
}
else if (current_angle > target_angle) {
    current_angle -= SERVO_SLEW_STEP;
    if (current_angle < target_angle) current_angle = target_angle;
}
```

1° / 20 ms = **50 °/s**,全程 -90°→+90° 需 3.6 s。

这段代码有两个容易写错、而这里写对了的地方:

1. **两个方向的 `if` 都要有防过冲钳位**——否则每次都会冲过目标值,再反向修正,产生极限环振荡。
2. **回传给上位机的是 `current_angle` 而不是 `target_angle`**——这样 VOFA+ 上能看到「指令 vs 实际」的跟随过程;传 `target_angle` 就只是一条阶跃线,失去调试价值。

## 7. 关键设计决策汇总

| 决策 | 理由 |
|---|---|
| 中断只搬字节,主循环解析 | 避免浮点解析阻塞中断、引入抖动 |
| `__disable_irq()` 保护 `rx_line` 拷贝 | 32 字节拷贝非原子,防撕裂读 |
| 回调内重新武装接收 | HAL 的 ReceiveToIdle 是一次性的,否则链路永久死掉 |
| `_Static_assert` 校验帧结构 | 把填充字节导致的协议错位提前到编译期 |
| 主循环忙等而非 `HAL_Delay` | 不依赖 SysTick,周期抖动更小 |
| 回传 `current_angle` 而非 `target_angle` | 保留跟随过程的可视化调试能力 |
| `servo_angle_to_pulse` 内做限幅 | 防止上位机下发越界角度导致舵机撞限位 |
| **不调用 `servo.c` 的 `pwm_start()`** | 会让 `pulse_6` 与主线抢 TIM4_CH4,见下节 |

### 7.1 通道争用问题(重要)

`main.c:187` 有一处刻意的注释:

```c
/* 不再调用 servo.c 的 pwm_start()/servo_reset_begin()：
   servo.c 会往 TIM4_CH4 (PD15) 写 pulse_6，与本文件的 VOFA 控制抢同一个通道 */
```

`servo.c` 的 `pwm_start()` 会启动 6 路 PWM,其中 `TIM4_CH4` 与主线舵机是**同一个物理通道**。若调用它,`servo_control()` 之后每次 `translate_angle_to_pulse()` 都会覆盖主线写入的 CCR 值,表现为舵机被随机抢走控制权。

**这是当前代码刻意隔离两个模块的原因,不要"顺手"把它加回去。**

## 8. 遗留模块与已知问题

`servo.c` / `config.h` / `math.c` 是从另一个机械臂工程移植过来的,**目前编译进固件但不参与主流程**。以下是逐一核对出的问题,接手时请留意。

### 8.1 编译已通过、但调用即炸的问题

**① `servo.h` 声明了 7 个从未实现的函数**

| 函数 | `servo.h` 声明 | `servo.c` 实现 |
|---|---|---|
| `servo_test` | ✓ | ✗ |
| `servo_reset` | ✓ | ✗ |
| `servo_release` | ✓ | ✗ |
| `servo_lift_return` | ✓ | ✗ |
| `servo_transfer` | ✓ | ✗ |
| `blue_task` | ✓ | ✗ |
| `yellow_task` | ✓ | ✗ |

现在能链接通过,仅仅因为**没有任何代码调用它们**。一旦调用,立刻 `undefined reference`。`servo.h` 里还有 `blue_task` / `yellow_task` 的重复声明(第 44-51 行)。

**② `servo.c` 悬空的外部声明**

```c
extern TIM_HandleTypeDef htim3;  // servo.c:48
```

本工程**没有 TIM3**(`tim.c` 只定义了 `htim2` 和 `htim4`)。该变量从未被引用,所以链接器不报错——但它是一颗定时炸弹:任何人一旦在 `servo.c` 里用到 `htim3`,链接立刻失败。

**③ `pulse_4` 的注释已过期**

```c
double pulse_4;  // 只有 pulse_4 没有 extern，因为它在 main.c 里定义
```

实际上 `pulse_4` 就是在 `servo.c:15` 定义的,`main.c` 里根本没有它。注释是旧版本的残留。

### 8.2 架构层面的问题

**④ `config.h` 在头文件里定义变量**

```c
double angle_1;      // 这是「定义」,不是「声明」
double now_angle_1 = 0;
float  R = 5;
double pi = 3.141593;
```

头文件里的这些是**定义**(tentative definition)。一旦有两个 `.c` 文件包含它,链接期就会 `multiple definition`。正确写法是头文件里放 `extern double angle_1;`,定义放到某个 `.c` 里。

**当前没人包含它**(已全仓库核对),所以这属于**纯死代码**,可以安全删除。

**⑤ `math.c` 是空文件却被加入编译**

空翻译单元在 ISO C 下是非法的(GCC 只给警告)。删掉 `Core/Src/math.c` 和第 4 行 `#include "math.h"`,或往里面写点真东西。

**⑥ `servo.c` 是阻塞式设计,与实时控制不兼容**

`pwm_out()` 在插值过程中逐点调用 `HAL_Delay(20)`(最多 180 次迭代),`servo_control()` 结尾还有 `HAL_Delay(500)`。一次动作可以阻塞主循环数秒。

这与 `main.c` 的 20 ms 硬实时周期是**根本冲突**的。若日后要把机械臂接入主流程,**不能直接调用这些函数**,必须改写成与主线一致的非阻塞状态机。

### 8.3 工程配置问题

**⑦ `tools/flash.cfg` 硬编码了绝对路径**

```tcl
program "c:/Users/Xiezheng_kingdom/Desktop/RCTEST_VOFA/build/Debug/RCTEST_VOFA.elf" verify
```

换一台机器或改目录就失效。**推荐用 `tools/flash.sh`**(路径自动解析),把 `flash.cfg` 当作废弃文件处理。

**⑧ `.vscode/launch.json` 有两个同名配置**

两个配置都叫 `STM32Cube: Launch ST-Link GDB Server`,内容完全相同,调试启动时会弹出选择框。删掉其中一个即可。

**⑨ `.code-workspace` 文件放在 `Core/Src/` 下**

`Core/Src/PZtest.code-workspace` 和 `Core/Src/RCTEST_VOFA.code-workspace`。工作区文件按惯例应放在仓库根目录。

**⑩ 源码注释为 GBK 编码**

`servo.c` / `servo.h` / `config.h` / `canculate.h` 的中文注释是 **GBK**,而 `main.c` / `tools/flash.sh` 是 **UTF-8**。在 UTF-8 环境下打开前者会看到乱码:

```
* ����汾��V1.0       ← 实际是 "程序版本：V1.0"
```

统一转成 UTF-8 是个低风险、高收益的清理动作。

### 8.4 优先级建议

如果只做三件事,按这个顺序:

1. **删死代码**——删 `Core/Src/math.c`、`Core/Inc/config.h`、`Core/Inc/canculate.h`,以及顶层 CMakeLists 里对应的两行。风险为零,立刻减少困惑。
2. **修 `servo.h`**——删掉 7 个未实现的声明和 `htim3` 悬空 extern,避免日后踩坑。
3. **统一编码**——全部转 UTF-8,顺手把 `flash.cfg`、`launch.json` 的重复配置清理掉。

## 10. 扩展指南

### 10.1 增加一个 VOFA+ 通道

改 [Core/Src/main.c:27](Core/Src/main.c#L27):

```c
#define CH_COUNT 3              // 2 → 3
```

然后:
1. 在 `vofa_send()` 里填 `frame.fdata[2]`;
2. 把函数签名和调用处补上第三个参数;
3. `_Static_assert` 会自动校验新帧长,不用手算。

帧尾位置由结构体布局自动推导,**不需要**改 `tail` 的赋值。这就是把帧尾放进结构体的好处。

### 10.2 新增自己的源文件

在**顶层** [CMakeLists.txt:46](CMakeLists.txt#L46) 追加:

```cmake
target_sources(${CMAKE_PROJECT_NAME} PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/servo.c
    ${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/math.c
    ${CMAKE_CURRENT_SOURCE_DIR}/Core/Src/你的文件.c      # ← 加这里
)
```

**不要**改 `cmake/stm32cubemx/CMakeLists.txt`(会被工具重新生成覆盖)。

### 10.3 改外设配置

仓库没有 `.ioc`,所以有两条路:

- **手改**:直接编辑 `Core/Src/tim.c` / `usart.c` 的 `MX_*_Init()`,以及对应的 `HAL_*_MspInit()` 里的时钟和引脚配置。注意 **`USER CODE BEGIN/END` 标记之外的代码在重新生成时会被覆盖**。
- **重建**:用 STM32CubeMX 新建 `.ioc` 工程重新生成骨架,再把 `main.c` 中 `USER CODE` 区的内容移植过去。工程较大时更稳妥。

**规律**:凡是在 `/* USER CODE BEGIN xxx */ ... /* USER CODE END xxx */` 之间的代码是"你的",之外的会被工具覆盖。`main.c` 中所有业务逻辑都规规矩矩写在标记内,这是好习惯——**改动时请保持**。

### 10.4 提高实时性的方向

当前忙等主循环只适合单路舵机。若要扩展,按代价从低到高:

1. **把 20 ms 周期改成定时器中断驱动**——主循环变成 `while(1) { __WFI(); }`,控制逻辑搬进中断回调和状态机。
2. **接收改用 DMA + 环形缓冲**——消除第 5.4 节所述的 50 字节缓冲隐患。
3. **引入 FreeRTOS**——`Drivers` 下已有 CMSIS,但需自行添加 RTOS 源和 `FreeRTOSConfig.h`。
