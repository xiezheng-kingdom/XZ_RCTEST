# RCTEST_YUNTAI 开发文档

> 二自由度云台控制 · STM32H743VIT6
> 面向读者：战队新人（上手改代码）、考核评审（看设计思路）

---

## 0. 一句话概括

一块 STM32H743 驱动两路舵机组成的云台：上位机（VOFA+）通过串口用 **ASCII 文本**下发目标角度，云台按 **50°/s 的斜坡**平滑转过去，同时以 **JustFloat 二进制帧**回传当前角度和保护区状态——**超限的角度会被夹到安全区内，并被标记出来**。

当前分支：`RCTEST_YUNTAI_MOVE`

---

## 1. 硬件资源与代码的映射

这是读这个工程**第一张该看的表**。嵌入式代码和别的代码最大的区别是：每个变量背后都连着一根真实的引脚，所以先建立「功能 → 引脚 → 外设 → 代码」的对应关系。

### 1.1 云台两轴（当前有效功能）

| 功能 | 引脚 | 外设通道 | 代码位置 |
|---|---|---|---|
| 底座水平偏转（pan） | **PD15** | **TIM4_CH4** | [main.c](../Core/Src/main.c) `gimbal[0]` |
| 俯仰角（tilt） | **PD14** | **TIM4_CH3** | [main.c](../Core/Src/main.c) `gimbal[1]` |

### 1.2 串口

| 端口 | 用途 | 参数 | 代码位置 |
|---|---|---|---|
| **USART2** | 上位机 VOFA+（收指令 + 回传） | 115200 8N1 | `PC_RXbuff` / `vofa_send()` |
| **UART5** | 小车通信（已开中断，尚未接业务） | 115200 8N1 | `Car_RXbuff` |
| UART7 / USART3 | 已初始化，当前未使用 | 115200 8N1 | [usart.c](../Core/Src/usart.c) |

### 1.3 未被云台使用的引脚

| 资源 | 说明 |
|---|---|
| PA0–PA3 = TIM2_CH1–CH4 | 遗留六自由度机械臂的舵机口，当前不驱动 |
| PD13 = TIM4_CH2 | 已配置 PWM，当前不驱动 |

### 1.4 时钟树（决定了脉宽怎么算）

```
HSE 25MHz ──> PLL(M=2, N=64, P=2) ──> SYSCLK 400MHz
                                        │
                          ┌─────────────┴─────────────┐
                     HCLK = 200MHz            APB1 = 100MHz
                                                       │
                                       TIM4 计数时钟 = 200MHz  ← APB 分频≠1 时定时器时钟翻倍
                                                       │
                                          PSC = 199  →  1MHz 计数
                                          ARR = 19999 → 20000 计数 = 20ms 周期
```

**由此得到一条极好用的性质：1MHz 计数 + 20ms 周期，所以「比较值」的数值就是「微秒数」。**

舵机脉宽约定（`servo_angle_to_pulse()`）：

| 角度 | 高电平脉宽 | TIM 比较值 |
|---|---|---|
| −90° | 0.5 ms | 500 |
| 0° | 1.5 ms | 1500 |
| +90° | 2.5 ms | 2500 |

映射公式：

```
pulse = ((angle + 90) / 90 + 0.5) × 1000
```

> ⚠️ **注意**：[servo.c](../Core/Src/servo.c) 的注释里写着 `PSC = 72-1, ARR = 200-1`，那是旧板子（72MHz）的配置，**和本工程实际时钟对不上**。以 [tim.c](../Core/Src/tim.c) 的实测值为准。

## 2. 架构设计：这个工程是怎么搭起来的

这一节是文档的核心——**不只说「长什么样」，更说「为什么这么长」**。

### 2.1 设计起点：先把对外接口列清楚

设计一个控制工程，不要一上来就想函数怎么分文件。先回答：**这个系统对外要和谁打交道？**

```
        ┌──────────────────────────────────────────┐
        │              STM32H743                    │
        │                                           │
VOFA+ ──┤ USART2  文本指令 ──┐                       │
(上位机)│                    │                       │
        │                    ▼                       │
        │            [ 解析 → 限幅 → 状态 ]          │
        │                    │                       │
        │                    ▼                       │
  舵机 ─┤ PD15/PD14  PWM ◄───┘                       │
        │                                           │
VOFA+ ◄─┤ USART2  JustFloat 回传（状态可观测）        │
        └──────────────────────────────────────────┘
```

外接口就三样：**两路串口、两路 PWM、一个 20ms 时间基准**。整个架构就是围绕这三样组织的——**任何不直接服务于这三样的东西，都不该出现在主路径上。**

### 2.2 分层：三层，各自只干一件事

```
┌─────────────────────────────────────────────────────────┐
│  应用层   main.c 主循环                                  │
│  职责：决定「什么时候做什么」——节拍编排、状态推进         │
│        gimbal_update() / vofa_send()                     │
├─────────────────────────────────────────────────────────┤
│  领域层   协议 + 设备抽象（也在 main.c，但职责独立）      │
│  职责：决定「什么是合法的一帧指令 / 一个轴」              │
│        VofaFrame / GimbalAxis / gimbal_parse_target()    │
│        servo_protect_angle() / servo_angle_to_pulse()    │
├─────────────────────────────────────────────────────────┤
│  生成层   CubeMX 产出，不手改                             │
│  main.h / tim.c / usart.c / gpio.c / HAL / CMSIS         │
│  职责：把寄存器配置好，提供 HAL_xxx 接口                  │
└─────────────────────────────────────────────────────────┘
```

**为什么要分层？** 因为在嵌入式里，「配置」和「逻辑」改动的频率完全不同。CubeMX 生成的 `tim.c`/`usart.c` 你可能一年只碰一次（改引脚时重新生成），而控制逻辑你可能一天改十遍。**把稳定件和易变件分开**，改逻辑时就不用担心把时钟配置改坏。

> **一条实用的纪律**：CubeMX 重新生成代码时，只有 `/* USER CODE BEGIN */ ... /* USER CODE END */` 之间的内容会被保留。所以本工程把所有业务逻辑都放进 `main.c` 的 USER CODE 区，**不手动改 `tim.c` / `usart.c`**——这样引脚变更时重新生成一次即可，逻辑零损失。

### 2.3 数据流：单向、无回环

```
      中断上下文                        主循环上下文
┌────────────────────┐          ┌──────────────────────────┐
│ USART2 空闲中断     │          │ ① rx_line_ready?         │
│  HAL_UARTEx_        │  置标志  │    → 快照 + 清标志        │
│  RxEventCallback()  ├─────────►│    → gimbal_parse_target │
│  只做 memcpy        │          │         （限幅 / 锁存）   │
│  再重新武装接收     │          │                          │
└────────────────────┘          │ ② gimbal_update()        │
                                │    斜坡推进 + 写 PWM      │
       回传走另一条路 ↓          │                          │
                                │ ③ vofa_send()            │
                                │    回传三通道             │
                                │                          │
                                │ ④ 对齐到下一个 20ms       │
                                └──────────────────────────┘
```

**数据只往一个方向流**：`串口 → 解析 → 状态 → PWM / 回传`。没有任何一步会回头去读串口或反过来影响解析。这是刻意的——单向数据流意味着**任何时刻系统状态都能由「最近一次合法指令 + 时间」唯一确定**，出问题时容易复现、容易查。

### 2.4 六条硬规则（评审重点看这里）

这六条是这个工程真正的「设计」，代码只是它的表达：

**① 中断里只搬数据，不算、不打印。**
`HAL_UARTEx_RxEventCallback()` 里只有一句 `memcpy` + 置标志。**绝对不在中断里做浮点解析、`printf`、`HAL_Delay`**——它们会拖长中断时间，导致丢帧甚至串口溢出。
*（对比：早期代码在中断回调里直接打印调试信息，这是嵌入式最常见的坑。）*

**② 主循环不 `HAL_Delay`。**
`sleep` 期间 CPU 什么都做不了。本工程用「斜坡状态机 + 固定节拍」代替延时，`HAL_Delay(500)` 那种写法（见遗留的 `servo.c`）在新架构里被彻底去掉了。

**③ 状态集中在结构体里，输出只有一个出口。**
所有角度状态都在 `gimbal[]` 数组里，所有 PWM 写入都经过 `__HAL_TIM_SetCompare()` 这一处。**不允许别的地方偷偷改 PWM 比较值**——否则出现「谁把这个舵机带偏了」的问题时无从查起。

**④ 协议是契约，契约用编译期断言守住。**
`VofaFrame` 的字节布局必须精确到字节（多一个填充字节，上位机就解析不出来），所以用 `_Static_assert` 在**编译期**把它钉死，而不是靠人记得。

**⑤ 危险指令必须限幅，且限幅状态要能观测。**
超出 ±30° 的目标角不是丢弃，而是**夹到边界**并**置标志回传给上位机**。系统既要安全，也要让人知道「刚才发生了一次越界」。

**⑥ 生成代码和手写代码分开。**
业务逻辑只在 `main.c` 的 USER CODE 区，改引脚不丢逻辑。

## 3. 关键模块详解

### 3.1 `GimbalAxis` —— 用一个结构体消灭重复

```c
typedef struct {
    TIM_HandleTypeDef *htim;
    uint32_t           channel;
    float              target;    /* 上位机下发的目标角 */
    float              current;   /* 当前输出角，按斜坡跟随 target */
} GimbalAxis;

static GimbalAxis gimbal[2] = {
    { &htim4, TIM_CHANNEL_4, 0.0f, 0.0f },   /* [0] 底座水平 PD15 */
    { &htim4, TIM_CHANNEL_3, 0.0f, 0.0f },   /* [1] 俯仰     PD14 */
};
```

**设计意图**：两根轴除了「定时器+通道」不同，**行为完全一致**。把差异抽成数据（结构体字段），把共性抽成代码（一个 `for` 循环），于是：

- 加第三根轴 = 数组里加一行 + 改 `GIMBAL_AXIS_COUNT`（**不用写新逻辑**）
- 改一根轴的行为 = 改一处 `gimbal_update()`（**两根轴同时生效**）

这就是「二自由度」相对「六自由度」在代码上的本质收益：**不是少写几个函数，而是把「轴」变成了数据。**

### 3.2 VOFA+ JustFloat 协议 —— 上位机联调的通道

**下行（上位机 → 单片机）：ASCII 文本**

```
45,-30\n          →  底座 45°，俯仰 −30°
20\n              →  只改底座 20°，俯仰保持不动
-100,0\n          →  底座越界，夹到 −30° 并置保护区标志
```

文本协议的好处是**人可读、串口助手就能发、调试不需要上位机**。

**上行（单片机 → 上位机）：JustFloat 二进制帧**

```c
typedef struct {
    float         fdata[3];   /* 12 字节：底座角度 / 俯仰角度 / 保护区状态 */
    unsigned char tail[4];    /* 4 字节：00 00 80 7F（小端 +Inf，帧尾标识） */
} VofaFrame;

_Static_assert(sizeof(VofaFrame) == sizeof(float) * 3 + 4U,
               "VofaFrame has unexpected padding");
```

- 帧长固定 **16 字节**，小端
- 帧尾 `00 00 80 7F` 就是小端的 `+Inf`，是 JustFloat 的帧分隔符
- 第 3 通道是**保护区状态**：`1.0` = 刚被拦下过，`0.0` = 正常

**为什么这里用二进制、下行用文本？** 因为方向不同、需求不同：下行是人发的，可读性优先；上行是机器读的、每秒 50 帧，**带宽和解析确定性优先**。

> ⚠️ **这里的 `_Static_assert` 不是装饰**。结构体一旦因对齐产生填充字节，帧尾就不在预期的偏移上，上位机直接解析失败——而且这种 bug 在示波器上看不出来、串口助手看是乱码，极难排查。用编译期断言把它挡在编译阶段，是成本最低的防御。

### 3.3 `gimbal_parse_target()` —— 宽容解析，严格拒绝

```c
static void gimbal_parse_target(const char *line)
{
    char *end = NULL;
    const float pan = strtof(line, &end);

    if (end == line) return;          /* 行首不是数 → 整行丢弃 */

    gimbal_error = 0.0f;              /* 新指令：先清状态 */
    gimbal[0].target = servo_protect_angle(pan);

    const char *rest = end;
    while (*rest == ',' || *rest == ' ' || *rest == '\t') ++rest;
    if (*rest == '\0') return;        /* 只发了底座角 → 俯仰保持 */

    const float tilt = strtof(rest, &end);
    if (end == rest) return;          /* 逗号后不是数 → 俯仰保持 */
    gimbal[1].target = servo_protect_angle(tilt);
}
```

三条设计决策：

1. **两个数各自可选**——只发一个数时另一轴保持不动。这让上位机可以独立调试单轴。
2. **行首不是数就整行丢弃**——**关键**：如果用 `atoi` 这类「失败返回 0」的解析，一串乱码会被当成「归零指令」，舵机会自己跑到中位。用 `strtof` + 检查 `end == line` 才能区分「解析失败」和「真的是 0」。
3. **逗号/空格/Tab 都当分隔符**——容忍上位机的格式差异。

### 3.4 保护区 —— 分轴限幅 + 错误锁存

```c
static float servo_protect_angle(float angle)
{
    if (angle < PROTECT_ANGLE_MIN) { gimbal_error = 1.0f; return PROTECT_ANGLE_MIN; }
    if (angle > PROTECT_ANGLE_MAX) { gimbal_error = 1.0f; return PROTECT_ANGLE_MAX; }
    return angle;
}
```

**两个语义必须说清楚，这是本工程最容易被问到的点：**

- **分轴独立**：越界只影响越界的那根轴（夹到 ±30°），**另一根轴照常执行**。不是「一行有错整行作废」——因为两轴是独立自由度，一根越界没理由牵连另一根。
- **状态锁存**：`gimbal_error` 在**每条新指令开头清零**，一旦置位就**保持到下一次解析**。所以上位机看到的 `1.0` 不是一个瞬间脉冲，而是**一段持续的电平**，直到下一条合法指令到达。

```
时间轴 ──────────────────────────────────────────────────►
指令:   -100,0        10,0          20,5
标志:   ████████████████░░░░░░░░░░░░░░░░░░░░  ← 高位段 = 曾越界
        └ 越界，锁存 ┘ └ 新指令合法，清零 ┘
```

> 这样设计的原因：主循环 50Hz，若只置一个周期的标志，上位机的采样很容易错过。**锁存保证了「越界一定会被观测到」。**

### 3.5 斜坡与节拍 —— 用状态机替代 delay

```c
#define SERVO_SLEW_STEP   (1.0f)   /* 每周期 1° → 50°/s */
#define CTRL_PERIOD_MS    (20U)    /* 主循环周期 */

static void gimbal_update(void)
{
    for (uint32_t i = 0; i < GIMBAL_AXIS_COUNT; ++i) {
        GimbalAxis *axis = &gimbal[i];

        if (axis->current < axis->target) {           /* 朝目标靠一步 */
            axis->current += SERVO_SLEW_STEP;
            if (axis->current > axis->target) axis->current = axis->target;  /* 不过冲 */
        } else if (axis->current > axis->target) {
            axis->current -= SERVO_SLEW_STEP;
            if (axis->current < axis->target) axis->current = axis->target;
        }

        __HAL_TIM_SetCompare(axis->htim, axis->channel,
                             servo_angle_to_pulse(axis->current));
    }
}
```

**为什么要斜坡而不是直接跳？** 舵机是机械件，指令阶跃会让它全速冲过去——电流冲击大、齿轮磨损快、还可能因为惯性过冲。1°/周期 @ 20ms = **50°/s**，是机械上舒适的转速。

**为什么不用 `HAL_Delay` 做斜坡？** 因为延时期间 CPU 是死的，回传停止、串口可能溢出。现在的写法**每个周期只推进一小步就返回**，主循环照常跑回传和对齐——**同样实现平滑，但不阻塞任何东西**。

节拍对齐：

```c
const uint32_t tick = HAL_GetTick();
/* ... 解析 / 更新 / 回传 ... */
while ((HAL_GetTick() - tick) < CTRL_PERIOD_MS) { }
```

这保证上位机看到的采样率**恒定 50Hz**，曲线不会忽快忽慢。

### 4.3 VOFA+ 上位机配置

| 项 | 值 |
|---|---|
| 串口 | USART2 对应的 COM 口 |
| 波特率 | 115200 |
| 数据格式 | 8N1 |
| 协议 | **JustFloat** |
| 通道数 | 3 |

三个通道含义：

| 通道 | 含义 | 正常范围 |
|---|---|---|
| 0 | 底座角度（pan） | −30 ~ +30 |
| 1 | 俯仰角度（tilt） | −30 ~ +30 |
| 2 | 保护区状态 | 0.0 / 1.0 |

下发指令用 VOFA+ 的「命令」功能或任意串口助手，格式 `底座角,俯仰角`，例如 `20,-15`。

**建议的联调步骤**（由简到繁）：

1. 先只发 `0,0`，确认两轴回中位、回传曲线在 0 附近
2. 发 `30,0`，观察通道 0 是否**斜着爬**到 30（验证斜坡，不是跳变）
3. 发 `-100,0`，确认通道 0 停在 −30、通道 1 不动，且**通道 2 变成 1.0 并保持**
4. 再发一条 `0,0`，确认通道 2 回到 0.0
5. 发乱码（如 `abc`），确认**云台纹丝不动**（验证拒绝逻辑）

## 5. 常见改动怎么做

| 想做什么 | 改哪里 | 注意 |
|---|---|---|
| 改保护角范围 | [main.c](../Core/Src/main.c) `PROTECT_ANGLE_MIN/MAX` | 必须落在 ±90 内，否则脉宽会超舵机行程 |
| 改转速 | `SERVO_SLEW_STEP` | 单位是「度/周期」，× 50 才是 °/s |
| 改控制周期 | `CTRL_PERIOD_MS` | 改了要同步改 `SERVO_SLEW_STEP`，否则实际转速会变 |
| 加第三根轴 | `gimbal[]` 加一行、改 `GIMBAL_AXIS_COUNT`、`CH_COUNT` 改 4 | `_Static_assert` 会自动守住帧长；VOFA+ 通道数也要同步改 |
| 加一个回传通道 | `CH_COUNT` +1、`vofa_send()` 多填一个 `fdata` | 顺序要和 VOFA+ 里的通道顺序一致 |
| 改引脚/波特率 | 用 CubeMX 改，重新生成 | **不要手改 `tim.c`/`usart.c`** |
| 新增源文件 | `CMakeLists.txt` 的 `target_sources()` | 否则链接报错 |

### 一个值得做的改进方向

现在的节拍对齐是**忙等**：

```c
while ((HAL_GetTick() - tick) < CTRL_PERIOD_MS) { }
```

CPU 在这段时间里空转。更优雅的做法是**用定时器中断驱动**：开一个 20ms 的定时器（比如用 TIM4 更新中断），在中断里置标志，主循环改成：

```c
if (!ctrl_flag) continue;
ctrl_flag = 0;
/* 执行解析 / 更新 / 回传 */
```

这样 CPU 空闲时可以进低功耗，节拍也更准（不受主循环里其他任务耗时的影响）。**留作练习。**

### 为什么明确不调用 `servo.c`

[main.c](../Core/Src/main.c) 里有一段注释写明了原因：

```c
/* 不再调用 servo.c 的 pwm_start()/servo_reset_begin()：
   servo.c 会往 TIM4_CH4 (PD15) 写 pulse_6，与本文件的 VOFA 控制抢同一个通道 */
```

**`servo.c` 的 `pwm_start()` 会把 PD15（现在是云台底座轴）当成机械爪的第 6 个关节去写。**两个模块同时写同一个 `TIM4_CH4` 比较值 → 底座轴会被随机拽走。

这类问题在嵌入式里叫**资源竞争**，而且是「编译能过、逻辑也自洽、就是行为诡异」的那种——所以**新架构用 `GimbalAxis` 把「哪个轴用哪个通道」集中成一份唯一声明**，就是为了让这类冲突一眼可见。

> **建议**：如果确认不再需要机械臂功能，可以把 `servo.c` / `math.c` 从 `CMakeLists.txt` 的 `target_sources()` 里移除，让固件更干净。

## 7. 已知问题与技术债

按「影响 / 修复成本」排序，供后续改进：

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | 节拍用忙等 `while(HAL_GetTick()...)` | CPU 空转、无法低功耗 | 改用定时器中断置标志（见 §5） |
| 2 | `vofa_send()` 用阻塞 `HAL_UART_Transmit`（超时 20ms） | 115200 下 16 字节约 1.4ms，占掉 7% 周期 | 改 `HAL_UART_Transmit_IT` 或 DMA |
| 3 | `servo.c` 编译但不调用 | 固件体积、误导新人、潜在通道冲突 | 从 `target_sources()` 移除 |
| 4 | `servo.c` / `servo.h` 是 **GBK 编码** | 在 UTF-8 环境里注释全是乱码，无法维护 | 统一转 UTF-8（`main.c` 已是 UTF-8） |
| 5 | `config.h` 头文件里定义变量（无 `extern`） | 一旦被两个 `.c` include 就重定义报错 | 若启用，改成 `extern` 声明 + 单个 `.c` 定义 |
| 6 | `servo.h` 里 `blue_task()` / `yellow_task()` 重复声明两遍 | 无害但说明该文件已失修 | 随 `servo.c` 一起清理 |
| 7 | `rx_line` 固定 32 字节，超长行被截断 | 超长指令会被切成两条，可能解析出错误角度 | 加大缓冲，或在中断里做溢出丢弃 |
| 8 | `servo.c` 注释中的 `PSC=72-1/ARR=200-1` 与实际不符 | 误导 | 随 `servo.c` 清理 |
| 9 | UART5（小车）收数据后直接丢弃 | 功能未接 | 按需补业务 |
